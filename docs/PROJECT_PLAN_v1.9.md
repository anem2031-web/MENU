# خطة العمل الرسمية - مشروع المنيو الرقمي (كوفي الملقا)

**الإصدار:** 1.9  
**الحالة العامة:** متوقف مؤقتًا - المرحلة 3 بانتظار اختبار القبول الفعلي على جهاز المالك  
**التقنيات المعتمدة:** React 19 + TypeScript + Vite + Wouter + Tailwind CSS 4 + shadcn/ui + Radix UI + Lucide React + Sonner + Framer Motion + TanStack React Query + tRPC + Node.js + Express + Drizzle ORM + TiDB (MySQL-compatible) + Zod + bcryptjs + S3/IDrive e2 + Multer + Sharp + Vitest + pnpm.

## حالة البنية التحتية الحالية

- **مزود قاعدة البيانات:** TiDB.
- **نوع/توافق قاعدة البيانات:** MySQL-compatible.
- **اسم قاعدة البيانات:** `MENU`.
- **الحالة:** تم إنشاء قاعدة البيانات على TiDB مسبقًا.
- إنشاء قاعدة البيانات لا يعني اكتمال المرحلة 2؛ ما زال يلزم إعداد اتصال التطبيق، Drizzle ORM، الـ migrations، واختبارات القراءة والكتابة.

- عدم إنشاء جداول للسلة أو الطلبات أو المدفوعات أو حسابات العملاء.

### معيار القبول
- نجاح الاتصال بـ TiDB.
- نجاح تنفيذ migrations.
- نجاح القراءة والكتابة التجريبية من قاعدة البيانات.

### مخرجات التنفيذ
- تم تثبيت `drizzle-orm`, `mysql2`, `drizzle-kit`, `tsx`, و`dotenv` داخل حزمة قاعدة البيانات.
- تم إعداد اتصال TiDB الآمن عبر TLS/SSL باستخدام `mysql2`.
- تم ربط Drizzle ORM بالـconnection pool.
- تم إنشاء `src/schema.ts` للجداول: `users`, `cafe_settings`, `categories`, `products`.
- تم توليد migration أولى `0000_grey_jackal.sql` وتطبيقها بنجاح.
- تم توليد migration فهرسة `0001_modern_spiral.sql` وتطبيقها بنجاح.
- تم التحقق من وجود جداول `__drizzle_migrations`, `cafe_settings`, `categories`, `products`, `users` داخل قاعدة `MENU`.
- تم اعتماد فهرس مركب للمنيو على `products(category_id, is_visible, sort_order)` باسم `products_menu_lookup_idx`.
- تم اعتماد فهرس `products_available_idx` على `is_available`.
- تم التحقق من القيود والفهارس باستخدام `SHOW INDEX` مباشرة على TiDB.
- نجح اختبار كتابة/قراءة/حذف مباشر عبر `mysql2`.
- نجح اختبار كتابة/قراءة/حذف عبر Drizzle ORM.
- نجح `pnpm -C ../.. typecheck` لجميع حزم المشروع بدون أخطاء.

### ملاحظات التنفيذ
- قاعدة البيانات الفعلية: **TiDB / MENU**.
- TiDB Cloud يرفض الاتصالات غير المشفرة؛ تم اعتماد TLS مع `rejectUnauthorized: true`.
- الصور نفسها لن تُخزن داخل TiDB؛ سيتم رفعها إلى **IDrive S3/e2**، بينما تحفظ قاعدة البيانات مفاتيح وروابط الصور فقط.
- تم تأجيل جدول `product_images` المستقل لمرحلة الصور إذا احتجنا دعم أكثر من صورة لكل منتج؛ الـMVP يستخدم `image_key` و`image_url` في جدول `products`.
- ظهرت بيانات اعتماد قاعدة البيانات في المحادثة أثناء التشخيص؛ يجب تدوير/تغيير كلمة مرور TiDB قبل النشر النهائي وتحديث `.env` فقط، وعدم وضع الأسرار في Git.
- تحقق معيار قبول المرحلة 2 بالكامل: اتصال ناجح، migrations ناجحة، واختبارات قراءة/كتابة ناجحة.

### مخرجات التنفيذ

- إضافة `auth.login` و`auth.logout` و`auth.me` في tRPC.
- إضافة `admin.status` كإجراء محمي للتحقق من حماية جلسة الإدارة.
- تشفير كلمات المرور باستخدام bcryptjs بــ 12 rounds.
- إضافة Session موقعة بـ HMAC داخل Secure/HttpOnly Cookie مع مدة 12 ساعة.
- التحقق من المستخدم النشط من TiDB عند كل جلسة.
- إضافة سكربت `owner:create` لإنشاء/تحديث حساب المالك بدون تخزين كلمة المرور داخل الكود.
- تمرير Cookies في tRPC Client عبر `credentials: include`.
- حماية واجهة `/admin` وتحويل غير المسجل إلى `/admin/login`.

### ملاحظات التنفيذ
- بدأ تنفيذ المرحلة 3 رسميًا في 2026-09-29 16:37 +03.
- `Secure` يتم تفعيله تلقائيًا للكوكي في بيئة production، مع `HttpOnly` و`SameSite=Lax` دائمًا.
- لا يتم تخزين كلمة المرور الأصلية؛ يتم حفظ bcrypt hash فقط في جدول `users`.
- نجح فحص بنية المشروع بعد التعديلات عبر `node scripts/verify-structure.mjs`.
- تم التحقق من سلامة صياغة `pnpm-lock.yaml`.
- تعذر تنفيذ `pnpm install` و`pnpm typecheck` داخل بيئة التنفيذ الحالية بسبب عدم توفر الوصول إلى npm registry، لذلك لا يجوز إغلاق المرحلة هنا.
- معيار القبول النهائي للمرحلة يحتاج اختبارًا فعليًا على جهاز المالك: `pnpm install` ثم `pnpm typecheck`، إنشاء حساب مالك، تسجيل دخول، فتح `/admin`، تسجيل خروج، ثم التأكد من منع الدخول بدون جلسة.
